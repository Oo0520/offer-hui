Offer汇 · 应届生求职信息聚合平台
MVP 技术实施细案

聚合全网校招/实习信息 · 校招日历 · DDL 提醒 · AI 匹配 · 轻社区（不做招聘闭环，仅跳转官方入口）

技术栈：Next.js + Supabase + Python + Meilisearch MVP 周期：1 个月 定位：应届生求职信息中台
核心架构一句话

「Vercel(Web) + Railway/Fly.io(Python 服务) + Supabase(数据) + Meilisearch(搜索) + Redis/Arq(队列)」五块拆分；主链路「爬取→解析→入库→向量/索引→检索→提醒」；AI 只用在三个低成本节点（字段兜底、匹配摘要、top-k 解释），LLM 成本压到最低。

1. 最终技术架构（模块划分与通信）

① 客户端层 · Vercel（Edge / Serverless）
Next.js Web（移动优先）岗位/日历/看板/社区订阅页（邮件/WebPush/ICS）
② API / BFF 层 · Next.js API Routes（聚合 / 鉴权 / 转发）
/api/jobs/api/search/api/subscribe/api/match/ics/[token]
← HTTPS ↑ Supabase(RLS) · Meilisearch(搜索) · 入队提醒任务
③ Python 服务层 · Railway / Fly.io / Cloud Run（Docker）
爬虫服务（Scrapy/httpx/Playwright）解析服务（规则+spaCy+LLM兜底）匹配服务（pgvector+LLM摘要）通知服务（Resend/WebPush/ICS）调度器（APScheduler/cron）
④ 任务队列 · Redis + Arq（asyncio 原生 worker）
parse_jobvectorize_jobindex_jobremind_jobreconcile_job
⑤ 数据 / 外部依赖
Supabase（Postgres+pgvector · Auth · Storage · Realtime）Meilisearch（中文分词+筛选+排序）数据源(24365/高校/企业) · Resend · VAPID WebPush · LLM API

关键通信链路：浏览器→BFF→(Supabase 查询 / Meilisearch 搜索)；爬虫服务→数据源(HTTP)→Supabase(写入)→入队；worker→(LLM/Resend/Meilisearch/WebPush)；调度器→按 cron 发布爬取与提醒任务。

拆分理由：Vercel 的 Serverless 函数不适合长时爬虫与定时任务，必须迁到常驻容器；队列选 Arq 而非 Celery——asyncio 原生、只依赖 Redis、无 AMQP，与爬虫/httpx 异步栈天然匹配，1 个月 MVP 心智负担最小；Supabase 作为唯一权威数据源，Meilisearch 只做搜索索引（避免双主数据源不一致）。

  tags jsonb not null default '[]',
  content_hash text,                   -- 内容变更检测
  embedding vector(1536),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

);
create index idx_jobs_deadline on jobs(deadline_at);
create index idx_jobs_posted   on jobs(posted_at desc);
create index idx_jobs_status   on jobs(status);
create index idx_jobs_city     on jobs(city);
create index idx_jobs_industry on jobs(industry);
create index idx_jobs_jobtype  on jobs(job_type);
create index idx_jobs_cohort   on jobs(cohort);
create index idx_jobs_company  on jobs(company_id);
create index idx_jobs_tags     on jobs using gin(tags);
-- 数据量大后启用向量索引：
create index on jobs using hnsw (embedding vector_cosine_ops);
去重核心：unique(source, external_id) 是天然幂等键，配合 INSERT ... ON CONFLICT (source, external_id) DO UPDATE 实现 UPSERT。向量索引取舍：万级数据用 ivfflat(lists=100)；十万级再切 hnsw(m=16, ef_construction=64, ef_search=40)。

4. 爬虫模块设计

级别来源抓取方式说明
A国家24365（ncss.cn）优先官方 JSON/接口，否则列表页+详情页 HTML权威、robots 宽松
B高校就业信息网RSS / 规范列表页 / 分页 HTML配置驱动，每校一个 spider 配置
C企业官网校招页（/campus）HTML + 必要时 Playwright企业数量少、逐个接入
✗BOSS/智联/实习僧等商业平台不碰反爬严格 + 合规风险，MVP 明确排除

解析策略（三级）

  • 规则层：正则抽取薪资、学历、城市、届别；技能关键词表命中打标——覆盖约 80% 情况，零成本
  • spaCy NER：补充机构名、专业实体（zh_core_web_sm 或自训小型模型）
  • LLM 兜底：仅当字段置信度低于阈值（如薪资/学历未抽到）时，把字段片段丢给 LLM 结构化返回

去重与增量更新

external_id = sha256(source + source_url)   # 或直接用源站自带 ID
抓列表 → 逐条算 external_id → SELECT 已存在?
  新    → 入库(published) + 入队(parse+vectorize+index)
  已存在 → 对比 content_hash
           → 变：UPDATE + 重新向量化
           → 不变：跳过
  列表页已不存在的旧记录 → 标记 expired

失败重试与监控

  • Scrapy RetryMiddleware（3 次，指数退避，仅对 429/5xx/超时）
  • 单源连续失败 → 写 crawl_runs.error + crawl_sources.active=false 自动暂停 + Resend 告警
  • 每次调度写 crawl_runs 统计（found/new/updated/failed），供运营看板
  • 解析退化检测：字段解析失败率突增 → 自动切换手动导入兜底通道
合规红线：首次抓取前读并缓存 robots.txt（disallow 则跳过）；限速 CONCURRENT_REQUESTS=4 / DOWNLOAD_DELAY=1.5s + 随机 jitter；独立 UA（OfferHubBot/1.0 + contact）；只存公开信息、每行带 source + source_url、前端显著标注"以官方为准"；提供投诉/下架入口，源站要求即停止。

5. AI 匹配流程（伪代码）

# ===== 岗位侧：入库后异步处理 =====
async def task_parse_and_vectorize(job_id):
    job = fetch_job(job_id)
    fields = rules_extract(job.description + job.title)   # ① 规则+正则，低成本高覆盖
    fields |= ner_extract(job.description)                # ② spaCy NER 补充实体
    for f in ("salary","degree","city"):                  # ③ 仅低置信度字段走 LLM
        if fields[f].confidence < 0.6:
            fields[f] = llm_fallback(job.description, field=f)  # 小 prompt 只补单字段
    job.embedding = embed(f"{job.title} {job.industry} {job.city} "   # ④ 结构化字段向量
                          f"{fields.skills} {fields.degree} {job.tags}")
    job.fields = fields
    await upsert_job(job)
    await enqueue("index_job", job_id)                    # ⑤ 触发搜索索引同步

# ===== 用户侧：上传简历只做一次 =====
async def task_process_resume(resume_id):
    text = parse_pdf(resume.storage_path)
    resume.parsed_text = text
    resume.embedding = embed(text)                        # 简历全文向量，只生成一次
    resume.status = "ready"
    await upsert_resume(resume)

# ===== 匹配：请求 / 每日提醒共用 =====
async def match_jobs(resume_id, user_filters, top_k=30):
    resume = load_resume(resume_id)
    # ① 硬过滤先行（SQL 谓词缩小候选集）
    base_sql = """
        SELECT id, title, company_id, city, industry, job_type, salary_min,
               1 - (embedding <=> :q_vec) AS sim
        FROM jobs
        WHERE status='published' AND deadline_at > now()
          AND cohort = :cohort AND city = ANY(:cities) AND industry = ANY(:industries)
        ORDER BY embedding <=> :q_vec LIMIT :top_k
    """
    candidates = pgvector_search(base_sql, resume.embedding, filters=user_filters)
    # ② 规则重排：技能命中/学历/薪资预期加分
    for c in candidates:
        c.score = c.sim * 0.6 + rule_bonus(c, resume) * 0.4
    shortlist = sorted(candidates, key=lambda x: -x.score)[:10]
    # ③ LLM 只对 top-10 生成匹配理由 / 投递清单摘要
    reasons = llm_explain(shortlist, resume)
    return {"jobs": shortlist, "reasons": reasons}
相似度阈值建议（以 50~100 条人工标注校准）：cosine ≥ 0.35 进入候选池（召回宽）；≥ 0.55 标记"高匹配"（首页推荐位）。成本三板斧：简历向量只生成一次；岗位向量用结构化字段而非全文；LLM 只用于单字段兜底与 top-10 摘要 + 缓存。

6. 搜索同步方案（Meilisearch）

// 索引设置（jobs index）
{
  "primaryKey": "id",
  "searchableAttributes": ["title","company.name","city","industry","job_type","tags","description"],
  "filterableAttributes": ["city","industry","job_type","cohort","status","salary_min","salary_max","deadline_at","company_id"],
  "sortableAttributes": ["posted_at","deadline_at","salary_min","salary_max"],
  "rankingRules": ["words","typo","proximity","attribute","sort"],
  "synonyms": { "前端":["frontend","web前端"], "后端":["backend","服务端"], "算法":["algorithm"] }
}

同步策略（准实时 + 对账兜底）

写入路径：worker 入库成功 → enqueue("index_job", job_id)
index_job：POST /indexes/jobs/documents（add/update，按 primaryKey=id 幂等）

触发点：
  1) 新增/更新岗位 → index_job（准实时）
  2) 状态变更（expired）→ index_job 更新 status（前端 filter status=published 隐藏）
  3) 每日 reconcile_job：对比 DB 全部 published job_id 与索引
     → 缺失补同步、多余删除（防队列丢消息）

前端查询：/api/search → BFF 调 Meilisearch（search key）
  条件走 filter，排序走 sortableAttributes

中文分词如实说明：Meilisearch 内置 charabia 可满足 MVP 需求，但对长句/新词不够精准。对策：同义词字典归一领域术语 + 主字段(title/tags)命中；若后续不满意再评估换引擎，MVP 不为搜索精度返工。

7. 日历订阅实现细节（ICS）

订阅链接：https://offerhub.app/ics/{ics_token}/calendar.ics
ics_token：HMAC-SHA256(user_id, SECRET) 或 32 字节随机数（防遍历）

生成逻辑：
  - 数据：saved_jobs + subscriptions.filters 匹配的 published 岗位（上限 200 条/日历）
  - 每岗位一个 VEVENT：
      UID:    job-{job.id}@offerhub.app        # 稳定，防重复导入
      SUMMARY:【{cohort}】{title} · {company} 截止
      DTSTART: deadline_at（DTEND = +1h）
      URL:    apply_url（官方）
      VALARM: TRIGGER:-P1D（提前1天）+ TRIGGER:-PT6H（提前6小时）ACTION:DISPLAY
  - 头：X-WR-CALNAME: Offer汇-我的求职日历 / X-PUBLISHED-TTL: PT12H
  - 响应：Content-Type: text/calendar; Cache-Control: no-cache

刷新机制：Apple/Google/Outlook 周期性拉取 URL（约 24h~7 天），
         "实时生成 + no-cache" 即自动获得 DDL 提醒，无需主动推送。

用户管理：订阅页"复制日历链接"；"撤销订阅"= 重新生成 ics_token（旧链接失效）；
         默认只订阅"已收藏 + 筛选维度"岗位，避免日历被海量事件刷爆。

9. 风险与注意事项

维度风险对策
合规抓取边界、信息版权只抓公开信息 + 尊重 robots + 全量标注来源/官方跳转 + 不截留简历 + 投诉下架入口
反爬/封禁源站限流、改版限速 + 退避 + 失败降级手动导入 + 解析退化检测告警
成本LLM / Embedding 调用规则优先（80% 不调 LLM）、结构化字段向量化、缓存、只对 top-10 用 LLM
一致性队列丢消息 → 索引与 DB 不一致每日 reconcile 对账 + index_job 幂等
Supabase 配额连接池、RLS 误配worker 用连接池 + execute_many 批量；BFF 走 user 权限 + worker 用 service_role 限 IP

安全ICS token 遍历、简历泄露token 256bit 随机；Storage 桶 + RLS；VAPID 密钥保管；API 限流
范围控制一个月做不完主链路锁定「爬取→入库→列表/搜索→收藏→提醒」，AI 匹配作 V2 逐步点亮
